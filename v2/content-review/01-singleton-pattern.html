1. What is Singleton Pattern?

Definition

The Singleton pattern is a GOF Creational Pattern that restricts a class to exactly one instance across the entire JVM. It provides a global access point to that single instance through a static factory method. The class itself controls its own instantiation.

One line: Single means one, ton means object. A singleton class allows creating only one object.

In Java it is called a singleton Java class. In C# it is called a singleton C# class. Since it is a GOF pattern, it can be implemented in any OOP language (C++, Java, C#, Python, etc.).

Design patterns are defined by three parts

  1. Problem: The recurring issue in software development
  2. Solution: The best proven approach to solve it
  3. Context: The situation where this solution applies
Key Point

Not every solution is a design pattern. For a recurring problem, there can be many solutions. Only the best solution that has been proven across multiple projects is called a Design Pattern. The worst solution is called an Anti Pattern.

2. The Problem

Problem

Creating multiple objects for a Java class in the following situations is a waste of memory and CPU time:

  1. If the class has no member variables/attributes/properties (no state)
  2. If the class has read-only state (only final variables)
  3. If the class has sharable state (like cache or buffer)

In Java, object creation is a costly process in terms of memory and CPU utilization. Every new call allocates heap memory, runs the constructor, and initializes fields. If a class needs only one instance, creating more wastes resources.

Real-world analogy

Think of all employees in an office sharing a single printer. Every employee does not need their own printer. One printer serves everyone. If we design software for this office, the Printer class should be a singleton -- creating 100 Printer objects for 100 employees is wasteful when one object can serve all.

Three cases where singleton is needed

Case 1: Class with no state

A class that has no member variables, only methods. Creating multiple objects is pointless because every object behaves identically.

// No state -- all objects are identical
public class MathUtils {
    private MathUtils() {}

    private static MathUtils INSTANCE;

    public static MathUtils getInstance() {
        if (INSTANCE == null) INSTANCE = new MathUtils();
        return INSTANCE;
    }

    public int add(int a, int b) { return a + b; }
    public int multiply(int a, int b) { return a * b; }
}

// Can call methods for multiple times
// No need to create multiple objects
MathUtils.getInstance().add(10, 20);
MathUtils.getInstance().multiply(5, 6);

Case 2: Class with read-only state (final variables)

A class whose state is set once and never changes. Multiple objects all hold the same data.

// Read-only state -- all objects have same data
public class AppConfig {
    private static final String DB_URL = "jdbc:mysql://localhost:3306/bankdb";
    private static final int MAX_CONNECTIONS = 10;

    private static AppConfig INSTANCE;

    private AppConfig() {
        if (INSTANCE != null)
            throw new RuntimeException("Object already created");
    }

    public static AppConfig getInstance() {
        if (INSTANCE == null)
            INSTANCE = new AppConfig();
        return INSTANCE;
    }

    public String getDbUrl() { return DB_URL; }
    public int getMaxConnections() { return MAX_CONNECTIONS; }
}

Case 3: Class with sharable state (cache, buffer, pool)

A class that holds shared mutable state. Multiple objects would mean duplicate caches or connection pools, leading to inconsistency and wasted memory.

// Sharable state -- one connection pool serves all
public class ConnectionPool {
    private static ConnectionPool INSTANCE;
    private final List<Connection> pool = new ArrayList<>();
    private static final int POOL_SIZE = 10;

    private ConnectionPool() {
        for (int i = 0; i < POOL_SIZE; i++) {
            pool.add(createConnection());
        }
    }

    public static ConnectionPool getInstance() {
        if (INSTANCE == null)
            INSTANCE = new ConnectionPool();
        return INSTANCE;
    }

    public synchronized Connection getConnection() {
        if (pool.isEmpty()) throw new RuntimeException("Pool exhausted");
        return pool.remove(0);
    }

    public synchronized void releaseConnection(Connection conn) {
        pool.add(conn);
    }

    private Connection createConnection() {
        // create actual DB connection
        return DriverManager.getConnection(
            "jdbc:mysql://localhost:3306/bankdb", "root", "password");
    }
}

3. The Solution: Three Minimum Standards

Solution

A singleton class enforces single-instance creation through three rules:

  1. Private constructor (infact ALL constructors) -- prevents outsiders from using new operator to create objects
  2. Private static reference variable of class type -- holds the single instance. If null, object not yet created. If not null, object already exists.
  3. Public static factory method with singleton logic -- checks the reference variable, creates object only if null, returns existing object otherwise

Basic Singleton: Printer.java

package com.nt.sdp;

public class Printer {
    // Step 2: private static ref variable of class type
    private static Printer INSTANCE;

    // Step 1: private 0-param constructor
    private Printer() {
        System.out.println("Printer:: 0-param constructor");
    }

    // Step 3: static factory method having singleton logic
    public static Printer getInstance() {
        if (INSTANCE == null) {
            INSTANCE = new Printer();
        }
        return INSTANCE;
    }

    // business method
    public void printMessage(String msg) {
        System.out.println(msg);
    }
}

Note on constructor execution

We cannot always go by constructor execution to confirm whether an object is created. There are exceptional cases:

  • If you create an object for a subclass of an abstract class, the abstract class constructor will execute along with the subclass constructor. But that does not mean an object is created for the abstract class.
  • In Java, we cannot create objects for interfaces and abstract classes.
  • If the object is created using Cloning or Deserialization, the constructor will NOT be executed because the object is already initialized with data from the source.

Important Distinction

If a Java class allows creating only one object, but someone still creates one, that class is NOT called singleton. A class is singleton only when it forces/restricts object creation to one. Example: the Test class below is NOT singleton even though you only create one object:

public class Test {
    Test t = new Test();  // Creates only one, but nothing stops creating more
    // ...
    // "Test" is NOT a singleton Java class
}

Servlet component class is not a singleton -- ServletContainer is happy to create one object of Servlet, but it does not force the restriction. If you can bypass the container, you could create more objects.

5. Multithreading Problem

Critical Problem

The basic lazy singleton is NOT thread-safe. If multiple threads of the same Client App or different Client Apps call Printer.getInstance() simultaneously with improper thread switching while executing singleton logic, there is a possibility of creating multiple objects for the singleton class.

This is a serious problem when using singleton as a helper class for Servlet/JSP in a web application, which is a multithreaded environment where multiple threads will be created for multiple requests.

6. Six Thread-Safe Solutions

a) Synchronized static factory method

// In Printer.java
public synchronized static Printer getInstance() {
    // singleton logic
    if (INSTANCE == null) {
        try {
            Thread.sleep(10000); // simulate slow creation
        } catch (Exception e) {
            e.printStackTrace();
        }
        INSTANCE = new Printer();
    }
    return INSTANCE;
}

Since the synchronized method allows only one thread at a time inside the method, there is no problem of multithreading breaking singleton. However, every call acquires the lock, even after the object exists. This is slow.

Better: Place synchronized(){} block inside the method where the sensitive logic is, instead of making the whole method synchronized.

b) Synchronized block inside static factory method

public static Printer getInstance() {
    // singleton logic
    synchronized (Printer.class) {  // class level locking
        if (INSTANCE == null) {
            try {
                Thread.sleep(10000);
            } catch (Exception e) {
                e.printStackTrace();
            }
            INSTANCE = new Printer();
        }
    }
    return INSTANCE;
}
Why Printer.class?

We cannot use this inside a static method, so we cannot pass synchronized(this). To protect static properties of a class, we use class level locking by passing the class name in the form of java.lang.Class object: synchronized(Printer.class).

In Java, .class is a compiler-generated pre-defined public static property of every Java class, returning the object of java.lang.Class having the current class name and info.

Conclusion: If we want to pass a Java class in the app as input value, we can use ClassName.class or the object of java.lang.Class.

c) Double-checked locking (Best 1)

Recommended Approach 1
public class Printer {
    private static volatile Printer INSTANCE;

    private Printer() {
        System.out.println("Printer:: 0-param constructor");
    }

    public static Printer getInstance() {
        if (INSTANCE == null) {  // 1st NULL check (no lock)
            System.out.println("Printer.getInstance()[outside sync block]: "
                + Thread.currentThread().getName());

            synchronized (Printer.class) {  // class level locking
                System.out.println("Printer.getInstance()[inside sync block]: "
                    + Thread.currentThread().getName());

                if (INSTANCE == null) {  // 2nd NULL check (with lock)
                    try {
                        Thread.sleep(10000);
                    } catch (Exception e) {
                        e.printStackTrace();
                    }
                    INSTANCE = new Printer();
                }
            }
        }
        return INSTANCE;
    }
}

The first null check avoids the synchronized block entirely once the object is created. Only when INSTANCE is null do threads enter the synchronized block, and the second null check inside prevents duplicate creation. The volatile keyword ensures the INSTANCE field is visible across all threads immediately.

This is the most commonly used approach in production code.

d) Eager instantiation

public class Printer {
    // object created at class loading time itself (eager)
    private static final Printer INSTANCE = new Printer();

    private Printer() {
        System.out.println("Printer:: 0-param constructor");
    }

    public static Printer getInstance() {
        return INSTANCE;  // no checking needed
    }
}

Since the object is the static reference variable, the JVM creates it at class loading time. The object is created as soon as the class is loaded, even if it is never used. Thread-safe because class loading is inherently thread-safe in JVM.

Drawback: Creates the object even if never needed (no lazy loading).

e) Inner class based lazy instantiation (Bill Pugh - Best 2)

Recommended Approach 2
public class Printer {
    private Printer() {
        System.out.println("Printer:: 0-param constructor");
    }

    // Inner class -- loaded only when getInstance() is called
    private static class InstanceHolder {
        private static final Printer INSTANCE = new Printer();
    }

    public static Printer getInstance() {
        return InstanceHolder.INSTANCE;
    }
}

The key: the inner class InstanceHolder is NOT loaded when the outer class Printer is loaded. It is loaded only when getInstance() is first called. The JVM guarantees that class loading is thread-safe. No explicit synchronization needed.

This is the Bill Pugh Singleton -- it combines lazy initialization with thread safety and zero synchronization overhead.

f) ENUM based singleton (Best 3)

Recommended Approach 3
package com.nt.sdp;

public enum Printer3 {
    INSTANCE;  // enum constant -- internally: public static final Printer3 INSTANCE = new Printer3()

    public static Printer3 getInstance() {
        return INSTANCE;
    }

    // business method
    public void printMessage(String msg) {
        System.out.println("printing: " + msg);
    }
}

// Usage:
Printer3.INSTANCE.printMessage("Report #1234");

Why is Enum singleton the best?

  1. No multithreading issues: Eager instantiation happens on enum constant like INSTANCE. There will not be any multi-threading issue.
  2. Easy to develop: Writing less code with minimum coding standards.
  3. Clone-safe: The clone() method is marked as protected final in the internal default super class java.lang.Enum<E>. So we cannot override clone() in our enum. clone() cannot be called on enum constants. Every enum already extends java.lang.Enum<E> class internally. It cannot be extended further (Java does not support multiple inheritance). So our enum is NOT Cloneable by default.
  4. Serialization-safe: Every enum is Serializable by default. If we perform Serialization on enum constants, when we attempt to do Deserialization, we get already available enum obj/constant (i.e., some internal readResolve() method functionality is given).
  5. Reflection-safe: For enums, we cannot create objects using Reflection API as they do not contain constructors.

Enum inheritance hierarchy

java.lang.Object | extends | java.lang.Enum<E> ----implements----> java.lang.Comparable<E> | java.io.Serializable | extends (internally by compiler) | com.nt.sdp.Printer3 (enum -- internally class)

Enum singleton limitations

  • a) We cannot apply few features of Java on enum like inheritance using "extends"
  • b) We cannot place instance, static member variables in the enum representing the state of the object
  • c) We cannot place serialVersionUID while working with Enum to perform serialization activity
  • d) Eager instantiation based singleton is not ideal if the object is never used

7. Breaking Singleton (and How to Prevent)

a) Breaking via Cloning

If a singleton class implements Cloneable (directly or through inheritance), calling clone() creates a second object.

java.lang.Cloneable (I) java.io.Serializable (I) | | implements implements | | com.nt.util.CommonUtils (C) | extends | com.nt.sdp.Printer (C) Note: Even if Printer does not directly implement Cloneable, it inherits it from CommonUtils. Cloning is now possible.

Prevention: Override clone()

// Option 1: Return existing instance (not recommended)
@Override
public Object clone() throws CloneNotSupportedException {
    return INSTANCE;
}

// Option 2: Throw exception (BEST solution)
@Override
public Object clone() throws CloneNotSupportedException {
    throw new CloneNotSupportedException(
        "In this singleton class, cloning is restricted");
}

b) Breaking via Serialization and Deserialization

Problem

The process of converting a Java object's data into a stream of bits and bytes is called Serialization. These bits/bytes can be written to a file or sent over a network. Serialization is possible only on Serializable objects (class must implement java.io.Serializable).

If we perform Serialization on the singleton object and write its data to a file, we can then create as many objects as we want by reading from that file through Deserialization.

Java App File +-----------+ Serialization +--------+ | singleton | (ObjectOutputStream) | ... | | object | ----bits/bytes--------> | bits | | (java | | bytes | | data) | +--------+ +-----------+ | | +-----------+ DeSerialization | | NEW Java | (ObjectInputStream) <------+ | object | +-----------+ When object is created through DeSerialization, the constructor will NOT be executed because the newly created object is already initialized with data collected from the file/network. So separate initialization via constructor is not required.

Prevention: readResolve() method

// Add this method in your singleton class
private Object readResolve() throws ObjectStreamException {
    return INSTANCE;
}

Important Note on serialVersionUID

We never make a singleton class implementing Serializable directly, but it may implement indirectly because classes in the inheritance hierarchy may implement Serializable. In that case, Serialization and Deserialization on the singleton object is possible.

It is recommended to add serialVersionUID to every Serializable class so we will not get InvalidClassException even though the class structure is changed at the time of DeSerialization:

private static final long serialVersionUID = 1L;

If serialVersionUID is not placed, the JVM generates a dynamic one based on the structure of the class. If the structure is modified during DeSerialization, we get:

c) Breaking via Reflection API

Even if the constructor is private, the Reflection API can access it, set it accessible, and create multiple objects. This breaks the singleton guarantee.

package com.nt.test;

import java.lang.reflect.Constructor;

public class SingletonReflectionTest {
    public static void main(String[] args) throws Exception {
        // Normal way -- gives single object
        Printer p1 = Printer.getInstance();

        // Reflection API way -- breaks singleton
        Class c = Class.forName("com.nt.sdp.Printer");
        Constructor[] cons = c.getDeclaredConstructors();
        cons[0].setAccessible(true);  // bypass private access
        Printer p2 = (Printer) cons[0].newInstance();

        System.out.println(p1.hashCode() + " " + p2.hashCode());
        // Output: DIFFERENT hashCodes -- singleton is broken!
        System.out.println("p1 == p2? " + (p1 == p2));  // false
    }
}

Prevention: isInstantiated flag

public class Printer {
    private static Printer INSTANCE;
    private static boolean isInstantiated = false;

    private Printer() {
        // Stop reflection-based second object creation
        if (isInstantiated) {
            throw new RuntimeException(
                "Object is already created. Cannot create another.");
        }
        isInstantiated = true;
        System.out.println("Printer:: 0-param constructor");
    }

    public static Printer getInstance() {
        if (INSTANCE == null)
            INSTANCE = new Printer();
        return INSTANCE;
    }
}

8. Breaking Singleton via ClassLoader

JVM internally uses a ClassLoader subsystem to load Java classes. The system has three classloaders:

ClassLoader Hierarchy (Parent Delegation Model): +-----------------------+ | BootStrap ClassLoader | Loading classes from <java_home>/jre/lib folder (jar files) | [a] | +-----------+-----------+ | | if not found (a,F) v +-----------------------+ | Extension ClassLoader | Loading classes from <java_home>/jre/lib/ext folder (jar files) | [b] | +-----------+-----------+ | | if not found (b,F) v +-----------------------+ | Application | Loading classes from the jar files, directories added to | ClassLoader [c] | CLASSPATH env... variable +-----------------------+ | | (c,F) if not found v ClassNotFoundException / NoClassDefFoundError Request to load a class: [c] Application CL receives request --> delegates to parent [b] Extension CL --> delegates to parent [a] BootStrap CL --> [a] searches rt.jar etc. If found, loads it. --> If not found, [b] searches ext folder. --> If not found, [c] searches CLASSPATH. --> If still not found, throws exception.

Notes on ClassLoader behavior

  • If a class is loaded by parent classloader, the same class will NOT be loaded by child classloader (Principle of Delegation)
  • The class loaded by parent classloader is visible to child classloader, but not the reverse (Principle of Visibility)
  • When JVM gives a class to classloader subsystem for loading, it is delegated to all classloaders using the delegation principle

Breaking singleton using Custom ClassLoader

URLClassLoader is a readily available custom classloader which can load classes from specific jar files and also initialize them as needed.

// Using Application ClassLoader (default)
System.out.println("Using Application ClassLoader");
Printer p1 = Printer.getInstance();
Printer p2 = Printer.getInstance();
System.out.println(p1.hashCode() + " " + p2.hashCode());

System.out.println("---");

// Using Custom ClassLoader (URLClassLoader)
System.out.println("Using URLClassLoader");
URLClassLoader loader = new URLClassLoader(
    new URL[]{new URL("file:///c/myProj/jar5/1.jar")});
Class c1 = loader.loadClass("com.nt.sdp.Printer");
Constructor cons = c1.getDeclaredConstructors()[0];
cons.setAccessible(true);
Object obj = cons.newInstance();

System.out.println("object hash codes: " + obj.hashCode() + " " + p1.hashCode());
Using Application ClassLoader object hash codes: 1550009438 1550009438 Using URLClassLoader (separate Custom ClassLoader) object hash codes: 1300502809 895342119

Here URLClassLoader is an independent classloader and not linked with JVM's classloader system. So one object is created using ApplicationClassLoader of ClassLoader sub system and another object will be using URLClassLoader (custom classloader).

Practical Impact

There is no solution for this problem from the singleton Java class developer perspective. Because URLClassLoader can break any singleton Java class. The only practical advice is: do not allow untrusted jar files to create CustomClassLoader or use SecurityManager to restrict ClassLoader creation.

Fortunately, this is a rare scenario in production. It only occurs when someone deliberately creates a custom classloader.

    }

    private static class InstanceHolder {
        private static final AppLogger INSTANCE = new AppLogger();
    }

        return InstanceHolder.INSTANCE;
    }

    }

ConnectionPool.java (Double-Checked Locking Singleton)

package com.bookmyshow.singleton;

import com.bookmyshow.model.Connection;
import java.util.HashSet;
import java.util.LinkedList;
import java.util.Queue;
import java.util.Set;

/**
 * Database connection pool.
 * Double-checked locking singleton: lazy, thread-safe, minimal lock contention.
 */
public class ConnectionPool {
    private static volatile ConnectionPool INSTANCE;

    private final Queue<Connection> availableConnections;
    private final Set<Connection> usedConnections;
    private final int maxPoolSize;

    private ConnectionPool(int poolSize, String dbUrl) {
        this.maxPoolSize = poolSize;
        this.availableConnections = new LinkedList<>();
        this.usedConnections = new HashSet<>();

        for (int i = 0; i < poolSize; i++) {
            availableConnections.add(new Connection(dbUrl));
        }

        AppLogger.getInstance().info(
            "ConnectionPool initialized with " + poolSize + " connections");
    }

    public static ConnectionPool getInstance() {
        if (INSTANCE == null) {
            synchronized (ConnectionPool.class) {
                if (INSTANCE == null) {
                    String dbUrl = ConfigManager.INSTANCE.get("db.url");
                    int poolSize = ConfigManager.INSTANCE.getInt("db.pool.size", 10);
                    INSTANCE = new ConnectionPool(poolSize, dbUrl);
                }
            }
        }
        return INSTANCE;
    }

    public synchronized Connection getConnection() {
        if (availableConnections.isEmpty()) {
            AppLogger.getInstance().warn(
                "Connection pool exhausted. Used: " + usedConnections.size()
                + "/" + maxPoolSize);
            throw new RuntimeException("No available connections in pool");
        }
        Connection conn = availableConnections.poll();
        conn.setInUse(true);
        usedConnections.add(conn);
        return conn;
    }

    public synchronized void releaseConnection(Connection conn) {
        if (conn == null) return;
        conn.setInUse(false);
        usedConnections.remove(conn);
        availableConnections.offer(conn);
    }

    public int getAvailableCount() {
        return availableConnections.size();
    }

    public int getUsedCount() {
        return usedConnections.size();
    }
}

CacheManager.java (Inner Class Singleton with TTL)

package com.bookmyshow.singleton;

import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;

/**
 * In-memory cache with time-to-live (TTL) expiry.
 * Inner class singleton: lazy loaded, thread-safe.
 * Uses ConcurrentHashMap for thread-safe read/write.
 */
public class CacheManager {
    private final Map<String, CacheEntry> cache;
    private final long defaultTtlMs;

    private static class CacheEntry {
        final Object value;
        final long expiresAt;

        CacheEntry(Object value, long ttlMs) {
            this.value = value;
            this.expiresAt = System.currentTimeMillis() + ttlMs;
        }

        boolean isExpired() {
            return System.currentTimeMillis() > expiresAt;
        }
    }

    private CacheManager() {
        this.cache = new ConcurrentHashMap<>();
        int ttlSeconds = ConfigManager.INSTANCE.getInt(
            "cache.default.ttl.seconds", 300);
        this.defaultTtlMs = ttlSeconds * 1000L;

        AppLogger.getInstance().info(
            "CacheManager initialized with default TTL: " + ttlSeconds + "s");
    }

    private static class InstanceHolder {
        private static final CacheManager INSTANCE = new CacheManager();
    }

    public static CacheManager getInstance() {
        return InstanceHolder.INSTANCE;
    }

    public void put(String key, Object value) {
        put(key, value, defaultTtlMs);
    }

    public void put(String key, Object value, long ttlMs) {
        cache.put(key, new CacheEntry(value, ttlMs));
    }

    @SuppressWarnings("unchecked")
    public <T> T get(String key) {
        CacheEntry entry = cache.get(key);
        if (entry == null) return null;
        if (entry.isExpired()) {
            cache.remove(key);
            return null;
        }
        return (T) entry.value;
    }

    public void remove(String key) {
        cache.remove(key);
    }

    public void clear() {
        cache.clear();
    }

    public int size() {
        // Remove expired entries and return count
        cache.entrySet().removeIf(e -> e.getValue().isExpired());
        return cache.size();
    }
}

package com.bookmyshow.service;

import com.bookmyshow.model.Booking;
import com.bookmyshow.model.Connection;
import com.bookmyshow.model.Show;
import com.bookmyshow.singleton.AppLogger;
import com.bookmyshow.singleton.CacheManager;
import com.bookmyshow.singleton.ConfigManager;
import com.bookmyshow.singleton.ConnectionPool;
import java.util.List;

public class BookingService {
    private final AppLogger logger = AppLogger.getInstance();
    private final ConnectionPool pool = ConnectionPool.getInstance();
    private final CacheManager cache = CacheManager.getInstance();

    public Booking bookTicket(String userId, String showId, int seatCount) {
        int maxSeats = ConfigManager.INSTANCE.getInt(
            "booking.max.seats.per.transaction", 10);

        if (seatCount <= 0 || seatCount > maxSeats) {
            logger.error("Invalid seat count: " + seatCount
                + ". Max allowed: " + maxSeats);
            throw new IllegalArgumentException(
                "Seat count must be between 1 and " + maxSeats);
        }

        Connection conn = pool.getConnection();
        try {
            logger.info("Booking " + seatCount + " seats for user "
                + userId + " on show " + showId);

            // Find the show and reserve seats
            Show show = findShow(showId);
            if (show == null) {
                logger.error("Show not found: " + showId);
                throw new RuntimeException("Show not found: " + showId);
            }

            boolean reserved = show.reserveSeats(seatCount);
            if (!reserved) {
                logger.warn("Not enough seats for show " + showId
                    + ". Requested: " + seatCount
                    + ", Available: " + show.getAvailableSeats());
                throw new RuntimeException(
                    "Not enough seats. Available: " + show.getAvailableSeats());
            }

            double totalAmount = show.getPrice() * seatCount;
            Booking booking = new Booking(userId, showId, seatCount, totalAmount);

            // Invalidate show cache since seats changed
            cache.remove("shows_" + show.getMovieId());

            logger.info("Booking confirmed: " + booking.getId()
                + " | Amount: Rs " + totalAmount);

            return booking;
        } finally {
            pool.releaseConnection(conn);
        }
    }

    public boolean cancelBooking(Booking booking) {
        logger.info("Cancelling booking: " + booking.getId());
        booking.setStatus("CANCELLED");
        logger.info("Booking cancelled: " + booking.getId());
        return true;
    }

    private Show findShow(String showId) {
        // Search across all cached shows
        MovieService movieService = new MovieService();
        for (var movie : movieService.getAllMovies()) {
            List<Show> shows = movieService.getShowsForMovie(movie.getId());
            for (Show s : shows) {
                if (s.getId().equals(showId)) return s;
            }
        }
        return null;
    }
}

                "AppLogger must be same across all threads");

Key observations from the project

  1. Four singletons, four approaches: ConfigManager (enum), AppLogger (Bill Pugh), ConnectionPool (double-checked locking), CacheManager (inner class). Each chosen for a specific reason.
  2. All services share the same instances: MovieService and BookingService both call getInstance() and get the exact same object (verified by hashCode).
  3. Thread safety verified: 5 concurrent booking threads all get the same singleton instances and all bookings succeed without data corruption.
  4. Connection pool manages lifecycle: Connections are borrowed and returned. Pool never exceeds the configured size.
  5. Cache reduces DB calls: First movie list call hits DB. Second call returns from cache. No redundant queries.
  6. Configuration drives behavior: Pool size, cache TTL, max seats all come from properties file. No hardcoded values.
  7. Logger captures everything: Every operation is logged with timestamp, level, thread name, and message. Written to console and file simultaneously.

11. Smaller Example: Configuration Manager

Scenario

National Bank of India needs a centralized configuration manager for their banking application. The config manager loads database URLs, API keys, feature flags, and connection pool sizes from a properties file. Every service (Account Service, Transfer Service, Notification Service) must read from the same configuration. If each service creates its own config object, they might read stale or inconsistent data. The config must be loaded once, shared everywhere, and be thread-safe because multiple request threads access it simultaneously.

package com.nbi.banking.config;

import java.io.IOException;
import java.io.InputStream;
import java.io.ObjectStreamException;
import java.io.Serializable;
import java.util.Properties;
import java.util.Set;

public class ConfigManager implements Serializable {
    private static final long serialVersionUID = 1L;
    private static volatile ConfigManager INSTANCE;
    private static boolean isInstantiated = false;

    private final Properties properties;

    private ConfigManager() {
        // Reflection protection
        if (isInstantiated) {
            throw new RuntimeException(
                "ConfigManager is a singleton. Use getInstance() instead.");
        }
        isInstantiated = true;

        this.properties = new Properties();
        loadProperties();
    }

    public static ConfigManager getInstance() {
        if (INSTANCE == null) {
            synchronized (ConfigManager.class) {
                if (INSTANCE == null) {
                    INSTANCE = new ConfigManager();
                }
            }
        }
        return INSTANCE;
    }

    public String get(String key) {
        return properties.getProperty(key);
    }

    public String get(String key, String defaultValue) {
        return properties.getProperty(key, defaultValue);
    }

    public int getInt(String key, int defaultValue) {
        String value = properties.getProperty(key);
        if (value == null) return defaultValue;
        try {
            return Integer.parseInt(value.trim());
        } catch (NumberFormatException e) {
            return defaultValue;
        }
    }

    public boolean getBoolean(String key, boolean defaultValue) {
        String value = properties.getProperty(key);
        if (value == null) return defaultValue;
        return Boolean.parseBoolean(value.trim());
    }

    public Set getAllKeys() {
        return properties.stringPropertyNames();
    }

    public synchronized void reload() {
        properties.clear();
        loadProperties();
        System.out.println("Configuration reloaded successfully");
    }

    private void loadProperties() {
        try (InputStream stream = getClass().getClassLoader()
                .getResourceAsStream("application.properties")) {
            if (stream == null) {
                throw new RuntimeException(
                    "application.properties not found on classpath");
            }
            properties.load(stream);
            System.out.println("Loaded " + properties.size()
                + " configuration properties");
        } catch (IOException e) {
            throw new RuntimeException(
                "Failed to load configuration", e);
        }
    }

    // Serialization protection
    private Object readResolve() throws ObjectStreamException {
        return INSTANCE;
    }

    // Clone protection
    @Override
    protected Object clone() throws CloneNotSupportedException {
        throw new CloneNotSupportedException(
            "ConfigManager is a singleton. Cloning is not allowed.");
    }
}

12. When to Use and When NOT to Use

When to use Singleton

ScenarioExampleWhy Singleton
Configuration managementLoading app config from properties/yamlConfig is read-only after load. One source of truth for all services.
LoggingApplication-wide loggerAll components write to same log file. One writer prevents file corruption.
Database connection poolHikariCP, C3P0 pool managerOne pool shared by all threads. Multiple pools waste connections.
Cache managerIn-memory cache (Guava, Caffeine)One cache serves all reads. Duplicate caches waste memory and lose consistency.
Thread pool managerExecutor service managerOne pool controls thread count. Multiple pools can exhaust system resources.
Hardware accessPrinter spooler, file system accessOne manager coordinates access to shared hardware.
Registry / Service locatorJNDI lookup, bean factoryOne registry holds all references. Multiple registries cause inconsistency.

When NOT to use Singleton

ScenarioWhy NOTUse Instead
Classes with per-request stateEach request needs its own state (user data, session). Singleton shares state across all requests.New instance per request (prototype scope)
Unit testingSingletons carry state between tests. One test can pollute another. Hard to mock.Dependency injection with interfaces
When subclassing is neededSingleton has a private constructor. Cannot extend it. Limits flexibility.Factory pattern with interface
In distributed systemsSingleton is per-JVM. In a cluster with 10 JVMs, you have 10 instances, not one.Distributed cache (Redis, Hazelcast)
When lazy init overhead mattersDouble-checked locking adds complexity. If the class is always used, eager init is simpler.Eager init or Spring bean
God object / too many responsibilitiesSingleton should not become a dumping ground for unrelated state.Split into focused classes
Anti-pattern Warning

Singleton becomes an anti-pattern when:

  • It holds mutable state that changes per request (user sessions, request data)
  • It is used as a global variable to avoid passing dependencies
  • It makes unit testing impossible because you cannot inject mock implementations
  • It grows into a god class with 50+ methods doing unrelated things

Modern approach: Use dependency injection (Spring, Guice) to manage object lifecycle instead of manually coding singletons. Let the framework decide the scope.
