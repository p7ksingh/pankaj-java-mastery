1. What is Abstract Factory Pattern?

Definition

The Abstract Factory pattern is a GOF Creational Pattern also called Factory of Factories or Super Factory. It provides an interface for creating families of related or dependent objects without specifying their concrete classes.

One line: A factory that creates other factories, each producing a family of related products.

It is the advanced level of Factory and Factory Method patterns. While a Simple Factory creates one product type and Factory Method lets subclasses decide which product to create, Abstract Factory creates entire families of products that work together.

When does Abstract Factory apply?

In a Factory pattern, if multiple factories are creating and returning same family class objects (classes having common super class or interface), then we need the Abstract Factory pattern. It acts as a super class for the factories, providing standards to them toward object creation.

Relationship between all three factory patterns

PatternCreatesStructureAnalogy
Simple FactoryOne product type, multiple variants1 factory, N productsOne bakery making different cakes
Factory MethodOne product type, factory per variant1 abstract factory, N factory subclassesMultiple bakeries (Chennai, Noida) each making cakes their way
Abstract FactoryMultiple product families1 super factory returning N factories, each producing a familyA food court that has a bakery, a juice bar, and a snack counter

2. The Problem

Problem

When an application needs to work with multiple families of related products (e.g., JDBC vs Hibernate for database access, or Windows vs macOS for UI components), the client ends up tightly coupled to concrete implementations. Switching from one family to another requires changes throughout the application.

Problem scenario 1: DAO layer

A banking application uses JDBC for data access. The client directly creates EmployeeJdbcDAOImpl objects. When the team decides to switch to Hibernate, every service class that creates DAO objects must be changed.

Problem scenario 2: Beverage factory

A beverage company sells two product families: Fruit Juices (Mango, Orange, Mixed) and Health Drinks (Protein Shake, Energy Drink). Each has its own factory. The client must know which factory to use and how to create products from each. If a new product family is added (Smoothies), the client code must change.

Problem scenario 3: Cross-platform UI

An application needs to render UI on Windows (Windows buttons, Windows text fields, Windows checkboxes) and macOS (macOS buttons, macOS text fields, macOS checkboxes). Without Abstract Factory, the client has if/else everywhere to decide which component to create.

3. The Solution: Factory of Factories

Solution

Create an abstract factory interface/class that declares methods for creating each product in a family. Each concrete factory implements this interface and creates products for one specific family. The client works only with the abstract factory and abstract products, never knowing which concrete family it is using.

AbstractFactory (interface) +-- createProductA(): AbstractProductA +-- createProductB(): AbstractProductB / \ ConcreteFactory1 ConcreteFactory2 +-- createProductA() +-- createProductA() | returns ConcreteA1 | returns ConcreteA2 +-- createProductB() +-- createProductB() returns ConcreteB1 returns ConcreteB2 Product Families: Family 1: ConcreteA1 + ConcreteB1 (work together) Family 2: ConcreteA2 + ConcreteB2 (work together) Client knows: AbstractFactory + AbstractProductA + AbstractProductB Client does NOT know: which concrete factory or product is used

package com.nt.factory;

import com.nt.beverage.*;

public class HealthDrinkFactory implements BeverageFactory {
    public Object create(String type) {
        if ("protein".equalsIgnoreCase(type)) return new ProteinShake();
        if ("energy".equalsIgnoreCase(type)) return new EnergyDrink();

// Super Factory (Factory of Factories)
package com.nt.factory;

public class BeverageSuperFactory {
    public static BeverageFactory getFactory(String category) {
        if ("juice".equalsIgnoreCase(category)) return new JuiceFactory();
        if ("health".equalsIgnoreCase(category)) return new HealthDrinkFactory();
        throw new IllegalArgumentException("Unknown category: " + category);
    }
}

5. Example 2: DAO Abstract Factory (JDBC vs Hibernate)

This is the classic enterprise example. The application can switch between JDBC and Hibernate without changing service layer code.

ApplicationFactory (factory of factories) | v DAOFactory (abstract) / \ JdbcDAOFactory HibernateDAOFactory | | | | EmployeeJdbc EmployeeHibernate DAOImpl DAOImpl | | AccountJdbc AccountHibernate DAOImpl DAOImpl
// DAO interfaces
public interface IEmployeeDAO {
    void insert(EmployeeBO bo);
    EmployeeBO find(int empno);
}

public interface IAccountDAO {
    void createAccount(AccountBO bo);
    AccountBO findByNumber(String accountNo);
}

// JDBC implementations
public class EmployeeJdbcDAOImpl implements IEmployeeDAO {
    public void insert(EmployeeBO bo) {
        System.out.println("JDBC: inserting employee " + bo.getName());
    }
    public EmployeeBO find(int empno) {
        System.out.println("JDBC: finding employee " + empno);
        return null;
    }
}

public class AccountJdbcDAOImpl implements IAccountDAO {
    public void createAccount(AccountBO bo) {
        System.out.println("JDBC: creating account " + bo.getAccountNo());
    }
    public AccountBO findByNumber(String accountNo) {
        System.out.println("JDBC: finding account " + accountNo);
        return null;
    }
}

// Hibernate implementations
public class EmployeeHibernateDAOImpl implements IEmployeeDAO {
    public void insert(EmployeeBO bo) {
        System.out.println("Hibernate: saving employee " + bo.getName());
    }
    public EmployeeBO find(int empno) {
        System.out.println("Hibernate: loading employee " + empno);
        return null;
    }
}

public class AccountHibernateDAOImpl implements IAccountDAO {
    public void createAccount(AccountBO bo) {
        System.out.println("Hibernate: persisting account " + bo.getAccountNo());
    }
    public AccountBO findByNumber(String accountNo) {
        System.out.println("Hibernate: loading account " + accountNo);
        return null;
    }
}

// Abstract Factory
public abstract class DAOFactory {
    public abstract IEmployeeDAO getEmployeeDAO();
    public abstract IAccountDAO getAccountDAO();

    public static DAOFactory getInstance(String type) {
        if ("jdbc".equalsIgnoreCase(type)) return new JdbcDAOFactory();
        if ("hibernate".equalsIgnoreCase(type)) return new HibernateDAOFactory();
        throw new IllegalArgumentException("Unknown DAO type: " + type);
    }
}

// Concrete factories
public class JdbcDAOFactory extends DAOFactory {
    public IEmployeeDAO getEmployeeDAO() { return new EmployeeJdbcDAOImpl(); }
    public IAccountDAO getAccountDAO() { return new AccountJdbcDAOImpl(); }
}

public class HibernateDAOFactory extends DAOFactory {
    public IEmployeeDAO getEmployeeDAO() { return new EmployeeHibernateDAOImpl(); }
    public IAccountDAO getAccountDAO() { return new AccountHibernateDAOImpl(); }
}

// Application Factory (super factory)
public class ApplicationFactory {
    public static DAOFactory getDAOFactory(String type) {
        return DAOFactory.getInstance(type);
    }
}

Client code

// Service layer uses only interfaces and abstract factory
DAOFactory factory = ApplicationFactory.getDAOFactory("jdbc");  // or "hibernate"
IEmployeeDAO empDAO = factory.getEmployeeDAO();
IAccountDAO accDAO = factory.getAccountDAO();

empDAO.insert(new EmployeeBO("Rajesh", 50000));
accDAO.createAccount(new AccountBO("SAV2001", "Rajesh"));
// With "jdbc": JDBC: inserting employee Rajesh JDBC: creating account SAV2001 // With "hibernate" (change ONE string): Hibernate: saving employee Rajesh Hibernate: persisting account SAV2001
Advanced: Using Properties File

For even looser coupling, read the factory type from a properties file instead of hardcoding "jdbc" or "hibernate":

# dao.properties
dao.type=hibernate

// In ApplicationFactory:
Properties props = new Properties();
props.load(getClass().getResourceAsStream("/dao.properties"));
DAOFactory factory = DAOFactory.getInstance(props.getProperty("dao.type"));

Now switching between JDBC and Hibernate requires changing only the properties file. No recompilation.

Advanced: Using Reflection

For maximum flexibility, the factory class name itself can be read from configuration and instantiated via reflection. This way, even the factory class can be swapped without modifying any Java code:

# factory.properties
dao.factory.class=com.nbi.dao.HibernateDAOFactory

// In ApplicationFactory:
String className = props.getProperty("dao.factory.class");
Class c = Class.forName(className);
DAOFactory factory = (DAOFactory) c.getDeclaredConstructor().newInstance();

This is how frameworks like Spring achieve complete decoupling between the client and the implementation.

UIFactoryProvider.java (Super Factory)

package com.nbi.ui.factory;

public class UIFactoryProvider {

    public static UIFactory getFactory(String platform) {
        if (platform == null) {
            throw new IllegalArgumentException("Platform cannot be null");
        }

        switch (platform.toLowerCase()) {
            case "windows":
                return new WindowsUIFactory();
            case "macos":
            case "mac":
                return new MacOSUIFactory();
            default:
                throw new IllegalArgumentException(
                    "Unsupported platform: " + platform
                    + ". Supported: windows, macos");
        }
    }
}

LoginScreen.java

package com.nbi.ui.screen;

import com.nbi.ui.factory.UIFactory;
import com.nbi.ui.product.Button;
import com.nbi.ui.product.TextField;
import com.nbi.ui.product.Checkbox;

public class LoginScreen {
    private final UIFactory factory;
    private final TextField usernameField;
    private final TextField passwordField;
    private final Checkbox rememberMe;
    private final Button loginButton;

    public LoginScreen(UIFactory factory) {
        this.factory = factory;
        this.usernameField = factory.createTextField("Enter username");
        this.passwordField = factory.createTextField("Enter password");
        this.rememberMe = factory.createCheckbox("Remember me");
        this.loginButton = factory.createButton("Login");
    }

    public void render() {
        System.out.println("--- Login Screen (" + factory.getPlatformName() + ") ---");
        usernameField.render();
        passwordField.render();
        rememberMe.render();
        loginButton.render();
    }

    public void simulateLogin(String username, String password) {
        usernameField.setValue(username);
        passwordField.setValue(password);
        rememberMe.toggle();

        System.out.println("\nAfter user input:");
        usernameField.render();
        passwordField.render();
        rememberMe.render();

        loginButton.onClick(() ->
            System.out.println("  Logging in as: " + usernameField.getValue()));
    }
}

Application.java

package com.nbi.ui;

import com.nbi.ui.factory.UIFactory;
import com.nbi.ui.factory.UIFactoryProvider;
import com.nbi.ui.screen.LoginScreen;
import com.nbi.ui.screen.DashboardScreen;
import java.io.InputStream;
import java.util.Properties;

public class Application {
    public static void main(String[] args) {
        // Read platform from config
        String platform = readPlatform();
        System.out.println("Platform: " + platform);
        System.out.println();

        // Get factory for the platform
        UIFactory factory = UIFactoryProvider.getFactory(platform);

        // Scenario 1: Render Login Screen
        LoginScreen loginScreen = new LoginScreen(factory);
        loginScreen.render();
        System.out.println();

        // Scenario 2: Simulate user login
        loginScreen.simulateLogin("rajesh.kumar", "nbi@2026");
        System.out.println();

        // Scenario 3: Render Dashboard
        DashboardScreen dashboard = new DashboardScreen(factory);
        dashboard.render();
        System.out.println();

        // Scenario 4: Switch platform at runtime
        System.out.println("=== Switching to macOS ===");
        UIFactory macFactory = UIFactoryProvider.getFactory("macos");
        LoginScreen macLogin = new LoginScreen(macFactory);
        macLogin.render();
        System.out.println();

        DashboardScreen macDash = new DashboardScreen(macFactory);
        macDash.render();
    }

    private static String readPlatform() {
        try (InputStream is = Application.class.getClassLoader()
                .getResourceAsStream("ui.properties")) {
            if (is != null) {
                Properties props = new Properties();
                props.load(is);
                return props.getProperty("ui.platform", "windows");
            }
        } catch (Exception e) {
            System.out.println("Could not read config, defaulting to windows");
        }
        return "windows";
    }
}

        UIFactory factory = UIFactoryProvider.getFactory("macos");
        Button btn = factory.createButton("Test");
        assertTrue(btn instanceof MacOSButton);
    }

    @Test
    void getFactory_isCaseInsensitive() {
        UIFactory f1 = UIFactoryProvider.getFactory("WINDOWS");
        UIFactory f2 = UIFactoryProvider.getFactory("windows");
        assertEquals(f1.getPlatformName(), f2.getPlatformName());
    }

    @Test
    void getFactory_throwsForNull() {
        assertThrows(IllegalArgumentException.class,
            () -> UIFactoryProvider.getFactory(null));
    }

    @Test
    void getFactory_throwsForUnsupported() {
        assertThrows(IllegalArgumentException.class,
            () -> UIFactoryProvider.getFactory("linux"));
    }

    @Test
    void windowsFactory_createsConsistentFamily() {
        UIFactory factory = UIFactoryProvider.getFactory("windows");
        assertNotNull(factory.createButton("btn"));
        assertNotNull(factory.createTextField("field"));
        assertNotNull(factory.createCheckbox("check"));
    }

    @Test
    void macFactory_createsConsistentFamily() {
        UIFactory factory = UIFactoryProvider.getFactory("macos");
        assertNotNull(factory.createButton("btn"));
        assertNotNull(factory.createTextField("field"));
        assertNotNull(factory.createCheckbox("check"));
    }

    @Test
    void productsFromSameFactory_areConsistent() {
        UIFactory winFactory = UIFactoryProvider.getFactory("windows");
        UIFactory macFactory = UIFactoryProvider.getFactory("macos");

        // Windows products should be Windows type
        assertTrue(winFactory.createButton("x") instanceof WindowsButton);
        // macOS products should be macOS type
        assertTrue(macFactory.createButton("x") instanceof MacOSButton);
    }
}

Key observations from the project

  1. LoginScreen and DashboardScreen never import platform-specific classes. They work only with UIFactory, Button, TextField, Checkbox interfaces.
  2. Switching platforms requires changing one config value (ui.platform=macos). Zero code changes.
  3. Adding Linux support: Create LinuxButton, LinuxTextField, LinuxCheckbox, LinuxUIFactory, and add one case to UIFactoryProvider. No existing file is modified.
  4. Products within a family are consistent. WindowsUIFactory only creates Windows components. You cannot accidentally mix a WindowsButton with a MacOSTextField.
  5. The super factory hides all concrete factories. The client calls UIFactoryProvider.getFactory("windows") and gets back a UIFactory interface. It never knows about WindowsUIFactory.

7. When to Use and When NOT to Use

When to use Abstract Factory

ScenarioExampleWhy Abstract Factory
Multiple product familiesJDBC vs Hibernate DAO implementationsEach family has multiple related products that must work together
Cross-platform UIWindows vs macOS vs Linux componentsButtons, fields, checkboxes must all be from the same platform
Theme systemsLight theme vs Dark theme componentsAll themed components must match
Multi-vendor integrationAWS vs Azure cloud servicesStorage, compute, and messaging must all be from the same vendor
Test vs ProductionReal services vs Mock servicesAll dependencies must be consistently real or mock

When NOT to use Abstract Factory

ScenarioWhy NOTUse Instead
Single product typeOnly one product, not a familySimple Factory or Factory Method
Products are independentButton and database connection are unrelatedSeparate factories
Only one family existsNo need for abstraction over one implementationDirect instantiation
Simple applicationAbstract Factory adds many classes for simple casesSimple Factory
